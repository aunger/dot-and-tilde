# PR creation

## A PR is not always required

Before creating a PR, confirm one is warranted.
An author may legitimately decline to open a PR when addressing the issue needs no code change, when it cannot fix the issue, or when the issue is flawed or should not be acted upon.
In those cases, explain why in a comment on the issue instead of creating a PR.
The rest of this document applies only once you have decided a PR is the right artifact.

## One topic per PR

Do not combine unrelated work in a single PR. You may resolve multiple issues with one PR, but *only* if they're both symptoms of the same technical issue.

Each PR must originate from its own dedicated branch. If your branch is not clean, fix it now by making a new branch and cherry-picking commits.

## The PR's Title

The title must name the PR's *solution*. Only name the issue's *problem* if you have space for both.

Write the title to last: the merge can make it the commit subject, as "The description is the record" below explains.

## The PR's Description

Include the #XYZ issue number of the issue that this PR addresses. If the PR completes the issue, write "Fixes #XYZ". Explain how the changes fix the issue.

Post and edit the title and description through the GitHub MCP server's tools, not `curl` or `gh api`, as the "Mechanics" section of the `writing` skill says.

### The description is the record

The description outlives the review thread: after the merge it is the record of the change, and editing it then does not change a commit already built from it.
The repository's merge settings decide whether it enters history too.
GitHub can build a squash or merge commit's subject from the title, with `" (#N)"` appended, and its body from the description; a rebase merge keeps the branch's own commits instead.
Read `squash_merge_commit_title`, `squash_merge_commit_message`, `merge_commit_title`, `merge_commit_message` and `allow_rebase_merge` from the repository object in the GitHub API before relying on either.

Write it for the reader who arrives at the change during a bisect a year from now, with no thread in view:

- **It must stand alone**, without leaning on the thread or on the round it happened to be written in.
- **Do not address the reviewer.** "Fixed the nit from round 2" and "see my comment" say nothing to that reader.
  Describe the change as it now stands, not the path taken to reach it.
- **Send round-to-round chatter and supporting evidence to PR comments instead**, which do not enter history: the description carries what changed and why, not the commands, counts and citations that establish it.
- **Re-read the description at the end of every round**, with the thread hidden.
  You cannot tell from inside a round whether it is the last one.

## Test plan checkboxes

Do not add a checkbox, or otherwise state a requirement, for something the automated test suite already covers.
Reserve checkboxes for steps automated CI does not perform, such as manual verification or changes outside the repo.

## No bylines

Do not append any attribution byline, session URL, or "Generated by Claude" footer to commit messages, PR/issue descriptions, or comments. No `---` divider followed by attribution text. No `Co-authored-by: Claude` trailer in PR bodies.
This prohibits writing one; it does not oblige anyone to remove one that landed.
Reviewers do not enforce this rule and do not mention bylines in a review.
